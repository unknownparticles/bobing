## Context

当前所有逻辑都在 `src/main.jsx` 的 `App` 组件里:判奖在 `finishTurn` 和 `finishRobot` 各写一份(且结果不一致),回合推进靠嵌套 `setTimeout`,技能写死目标,奖项只是玩家身上的 id 数组,没有奖池库存。要实现 5 份 spec,需要把"规则与状态"和"界面与节奏"分开,否则判奖、库存、技能、终局这些规则无法单测,也无法让机器人和玩家走同一条路径。

约束:
- 目录不是 git 仓库,现有依赖全是 `latest`,没有测试框架。
- 不在本次变更内做音效、粒子、换皮、竖屏重排(P1、P2)。
- 前端规范里的 Motion、Zustand 不属于本次范围,不引入。

## Goals / Non-Goals

**Goals:**
- 判奖、奖池、技能、终局、机器人策略全部是无 React 依赖的纯逻辑,可在 Node 下单测。
- 玩家与机器人共用同一套"掷骰 → 判奖 → 发放 → 终局检查"流程和同一套技能校验。
- 机器人决策可复现(随机数来源可注入)。
- UI 只订阅状态并派发动作,回合节奏(动画时长、停顿)留在 UI 层。

**Non-Goals:**
- 不做存档、联机、多局统计。
- 不改视觉风格与布局,只增加结算页、技能目标选择和次数显示所需的最少界面。
- 不引入状态管理库。

## Decisions

### 1. 游戏内核放 `src/game/`,用 reducer 管状态

文件划分:
- `config.js`:奖项表(数量、积分、优先级)、轮数上限 `MAX_ROUNDS = 8`、技能初始次数、机器人性格表。所有数值只在此处定义。
- `rules.js`:`evaluateRoll(dice)`。
- `state.js`:`createGame(players)`、`reduce(state, action)`、积分与排名的派生函数。
- `skills.js`:`getLegalTargets(state, userId)`、`canUseSkill(state, userId, skill)`。
- `bots.js`:`decideSkill(state, botId, rng)`。

选 reducer 而不是继续用多个 `useState`,原因是技能、发放、终局需要在一次动作里原子地改多处状态;拆成多个 setter 容易出现中间态(例如奖项已发放但终局未检查)。

备选:继续用 `useState` 加辅助函数。不选,因为无法在不渲染组件的情况下测试"积分守恒"这类跨模块不变量。

### 2. 动作与节奏分离

reducer 只处理即时动作,不含定时器:
- `USE_SKILL { userId, skill, targetId? }`
- `ROLL { userId, dice }`:骰子点数由调用方传入,reducer 内部调用 `evaluateRoll` 并结算。
- `ADVANCE_TURN`:推进到下一位,处理保护到期、轮数加一、轮数上限终局。
- `RESTART`

随机数和动画留在 UI 层:UI 生成 `dice`,播放动画,动画结束后派发 `ROLL`。这样 reducer 对同样的输入永远得到同样的输出。

备选:让 reducer 内部掷骰。不选,因为测试状元耗尽、终局这类场景时需要构造指定点数。

### 3. 奖项用实例而不是 id 数组

玩家持有的奖项改为 `{ uid, awardId, seq }`,`seq` 是全局递增的获得序号。原因是顺手牵羊需要"积分最高,同分取最近获得"(player-skills spec),id 数组无法区分同类奖项的先后。夺取时整条实例转移,`seq` 保持不变还是更新为夺取时刻,采用**更新为夺取时刻**,这样"最近获得"语义一致。

### 4. 判奖实现:先统计点数分布,再按优先级匹配

`evaluateRoll` 先校验输入(长度 6、整数、1 到 6,否则抛 `RangeError`),再统计每个点数出现次数,然后按"状元各档 → 对堂 → 三红 → 四进 → 二举 → 一秀 → 无奖"顺序返回第一个命中的结果。状元内部顺序:六杯红、五红、状元插金花、四点红、遍地锦、六杯黑、五子登科。各档条件互斥,顺序不影响结果,但保持固定顺序便于对照 spec。

测试用表驱动:每个 spec 场景一条用例,另加"全部 6^6 = 46656 种有序结果都返回合法结果且与排序后的结果一致"的穷举检查,覆盖顺序无关性。

### 5. 库存耗尽按无奖,在 reducer 里处理

`ROLL` 先调用 `evaluateRoll`,若奖项剩余为 0,则不发放、不降级,事件里记录"某某已发完"。这符合 prize-pool spec,也让"积分守恒"不变量只依赖发放和夺取两个入口。

### 6. 保护状态用"保护到谁的下一回合开始"表达

玩家状态里存 `protectedUntilTurn`(使用者下一次回合的全局回合序号)。`ADVANCE_TURN` 开始新回合时清除已到期的保护。不用"按轮清除",因为保护期跨越的是"使用者下一回合前",和轮次边界不同。

### 7. 机器人决策是纯函数,随机数注入

`decideSkill(state, botId, rng)` 返回 `null` 或 `{ skill, targetId }`,`rng` 是返回 `[0,1)` 的函数,默认 `Math.random`,测试里传固定序列。决策结果必须再通过 `canUseSkill` / `getLegalTargets` 校验后才派发,保证机器人与玩家走同一条规则(bot-personalities spec)。

### 8. UI 回合循环用单个 effect 驱动

用一个 `useEffect` 监听 `state.currentIndex` 与 `state.status`:轮到机器人时,先 `decideSkill` 并展示技能反馈,再延时执行掷骰动画、派发 `ROLL`、派发 `ADVANCE_TURN`。取代现在的嵌套 `setTimeout`,并在清理函数里清除定时器,避免快速重开局时旧定时器继续推进状态。

## Risks / Trade-offs

- [真实博饼规则存在地区差异,状元分档和积分可能与用户期望不同] → 所有档位和积分集中在 `config.js`,spec 里的表就是依据;需要用户确认(见 Open Questions)。
- [重写判奖会改变现有体验:原先只数 4 的个数,现在对堂、四进会出现] → 属于有意修正;奖池里本来就有这些奖项,之前是永远拿不到。
- [机器人技能让玩家的奖项会被夺走,挫败感可能上升] → 保护伞对玩家可用,且每个机器人的夺取次数有限(每人最多 2 次);P1 阶段再根据手感调数值。
- [`evaluateRoll` 穷举测试 46656 次,测试耗时] → 纯函数,预计毫秒级,可接受。
- [引入 vitest 属于新增 devDependency] → 固定精确版本,仅用于测试,不进入生产包。
- [目录不是 git 仓库,大改动无法回滚] → 实施前先 `git init` 并提交现状作为基线(见 tasks 第一组)。

## Migration Plan

1. `git init`,提交当前原型作为基线(提交需用户确认)。
2. 先落地 `config.js` 与 `rules.js` 并通过测试,此时 UI 不变。
3. 落地 reducer,UI 切换到 reducer,删除 `main.jsx` 中旧的判奖与技能代码。
4. 增加结算页、技能目标选择、次数显示和事件记录。
5. 每一步完成后运行 `npm run build` 与测试。回滚方式:回到基线提交。

## Open Questions

1. 状元分档与积分是否按上述标准博饼规则?默认按 spec 中的表;如需自定义规则(例如把对堂并入状元),只需改 `config.js` 与对应 spec。
2. 注册页的"观察者"身份:实现(例如机器人行动前显示其下一步倾向)还是移除?默认**移除**该选项并保留昵称与头像,因为实现它不在 P0 范围内;如果要保留,需要单独开一个变更。
3. 轮数上限 8 和技能次数(牵羊 2、保护伞 1)是否合适?这些是初始平衡值,实现后可按试玩调整。
